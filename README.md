# Payload Portfolio

Bilingual (FR/EN) developer portfolio fully driven by a CMS: content, sections, theme and SEO are all managed from the Payload admin panel — no code changes needed.

**Stack**: [Next.js 16](https://nextjs.org) (App Router) · [Payload CMS 3](https://payloadcms.com) · PostgreSQL · [Tailwind CSS 4](https://tailwindcss.com) · TypeScript · React 19 · [Motion](https://motion.dev)

## Features

- **Bilingual FR/EN** — native Payload localization (French by default with automatic fallback), language detection via middleware and `/fr` / `/en` prefixed routes
- **Light/dark theme** — flash-free toggle (`next-themes`), accent color configurable from the admin (Global Settings → Theme), optional dark-mode variant for project logos
- **Modular sections** — every home page section (hero, projects, experience, education, skills, about, testimonials, contact) can be toggled on/off and its copy edited from the admin
- **Manual display order** — an `order` field on projects, experiences, education and journal entries: `1` shows first, entries without a value follow sorted by date
- **Journal** — personal entries (travel, sport, events…) with filterable categories and public/private visibility
- **SEO** — metadata generated by `@payloadcms/plugin-seo` for projects, journal and hero; robots.txt, and a sitemap covering every page in both locales (homepage, projects archive, journal, and each detail page) with `hreflang` alternates
- **Social preview cards** — every page generates its own 1200x630 OG image (`opengraph-image.tsx`) with the site's accent color, the page title and its metadata. An image chosen in a document's SEO tab overrides it
- **Projects archive** — `/projects` lists every published project with a filter by technology, alongside the homepage section
- **Contact notification** — an optional email (via Resend) the moment the contact form is submitted, so a message is not only visible in the admin panel
- **Automatic revalidation** — every change in the admin regenerates the site (with 60s ISR as a safety net)
- **Uploads** — local disk in development, [Vercel Blob](https://vercel.com/docs/storage/vercel-blob) in production (automatic switch based on token presence)

## Quick start

Requirements: Node 24+, pnpm, PostgreSQL (or Docker).

```bash
git clone <repo>
cd payload-portfolio
cp .env.example .env   # set DATABASE_URL and PAYLOAD_SECRET
pnpm install
pnpm dev
```

Open <http://localhost:3000/admin> and follow the on-screen instructions to create the first admin user. The public site is at <http://localhost:3000>.

### With Docker

The `docker-compose.yml` starts the app (with hot reload) and PostgreSQL:

```bash
docker compose up -d
```

The database is exposed on `127.0.0.1:5432`, the site on port 3000. The container's `DATABASE_URL` is set in the compose file; `.env` is still used for everything else.

> **macOS note**: the file watcher may miss changes made through the Docker volume. If a code change doesn't seem to apply: `docker exec payload-portfolio-payload-1 touch <file>` or restart the container.

## Environment variables

| Variable | Description |
| --- | --- |
| `DATABASE_URL` | PostgreSQL connection string |
| `PAYLOAD_SECRET` | Payload secret key (sessions, tokens) |
| `NEXT_PUBLIC_SITE_URL` | Public site URL (SEO, sitemap) |
| `BLOB_READ_WRITE_TOKEN` | *Optional locally.* Vercel Blob token — without it, uploads go to local disk |
| `RESEND_API_KEY` | *Optional.* Enables the contact-form email notification. Without it, messages are only stored in the admin |
| `CONTACT_NOTIFICATION_FROM` | Sender address for that notification, on a domain verified with Resend |
| `CONTACT_NOTIFICATION_TO` | Recipient. Defaults to Global Settings → contact email |

## Content model

### Collections

| Collection | Purpose |
| --- | --- |
| **Projects** | Portfolio projects — rich description, cover image (+ dark variant), gallery, technologies, GitHub/live links, status, year, featured flag |
| **Experiences** | Professional timeline — position, company, technologies, dates |
| **Education** | Education timeline — degree, school, dates |
| **Skills** | Skills grouped by category |
| **Journal** | Personal entries with category, gallery and visibility |
| **Technologies** | Reusable tech tags (logo, color, website) |
| **Companies / Schools** | Company/school references (logo, website) |
| **Categories** | Shared taxonomy (tech, project, journal) |
| **Testimonials** | Testimonials |
| **Messages** | Contact form submissions |
| **Media** | Uploads (images, logos) |
| **Users** | Admin accounts |

### Globals

`Hero`, `About`, `Contact`, `Navigation`, `Footer`, `GlobalSettings` (theme, social links), `SectionsVisibility` (show/hide each section), `SectionsContent` (section titles and intros).

### Display order

Projects, experiences, education and journal entries have an optional **Order** field: `1` shows first, `2` second, and so on. Entries without a value follow, sorted by date (year for projects, start date for experience/education, date for journal). Featured projects and journal entries always come first.

## Migrations

The Postgres schema is versioned in [`src/migrations/`](src/migrations/). In development, Payload syncs the schema automatically (push mode); migrations are mainly for production:

```bash
pnpm payload migrate:status   # list pending migrations
pnpm payload migrate          # apply them
```

After any schema change: write/generate the matching migration, then run `pnpm generate:types`.

## Tests

- **Unit** (`tests/unit`) — pure logic, no database. Anything with I/O is mocked.
- **Integration** (`tests/int`) — the real Payload Local API against a throwaway `payload-portfolio-test` database, configured in [`.env.test`](.env.test). Postgres creates it on first run; every run drops it and rebuilds it with `payload migrate:fresh`, so the suite also proves the migrations still build a working schema from scratch. It refuses to start unless `DATABASE_URL` is a local database named `*-test`, and never reads `.env`.
- **Component** (`tests/dom`) — React components with Testing Library in jsdom.
- **E2E** (`tests/e2e`) — frontend and admin via Playwright, against a production build (`next build && next start` on port 3100) and its own `payload-portfolio-e2e-test` database, configured in [`.env.e2e`](.env.e2e). [`tests/e2e/serve.ts`](tests/e2e/serve.ts) rebuilds the database from the migrations, seeds the content in [`tests/e2e/fixtures.ts`](tests/e2e/fixtures.ts), then builds into `.next-e2e` — a separate directory, so an e2e build and a regular build never share a data cache. Specs that edit content do it through the REST API and put it back. Two Playwright projects: desktop Chromium runs everything; `mobile-safari` (iPhone 15 on WebKit) runs the navigation and mobile-menu specs. Run `pnpm exec playwright install chromium webkit` once before the first local run.

```bash
pnpm test:unit        # no setup needed
pnpm test:int         # needs local Postgres (docker compose up postgres)
pnpm test:e2e         # needs local Postgres; builds the site first (~2 min)
pnpm test:e2e:serve   # keep a seeded server up on :3100 — test:e2e reuses it
pnpm test:e2e:ui      # Playwright UI mode: run specs one by one, step through a timeline of each
pnpm test:e2e:report  # open the HTML report of the last run
```

A failing e2e test keeps a video, a screenshot and a full trace (DOM, network and console at each step). All of it is in the HTML report — locally with `pnpm test:e2e:report`, and on CI in the `playwright-report` artifact of the run (download it, then `pnpm exec playwright show-report <folder>`).

## CI/CD

- **GitHub Actions** ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) runs on every push to `main`/`staging` and on pull requests, as four parallel jobs: lint + typecheck; unit tests with the coverage thresholds; integration tests against a PostgreSQL service that starts empty and is built from the migrations alone (`PAYLOAD_DB_PUSH=false`), so a migration that no longer applies to a fresh database fails the build; e2e tests against a seeded production build (the Playwright report is attached to the run). Every job is skipped when the code was already tested: the `pull_request` run of the `staging` → `main` PR (the `push` run on `staging` tests the same commit), and the release-please version PR and its merge into `staging` (see [Versioning](#versioning)).
- **Release** ([`.github/workflows/release.yml`](.github/workflows/release.yml)) — see [Versioning](#versioning).
- **Vercel** builds with `pnpm run ci` ([`vercel.json`](vercel.json)), which applies pending migrations to the production database before `next build` — the schema can never lag behind the deployed code. Only `main` (production) and `staging` (preview) are deployed: `git.deploymentEnabled` in the same file blocks every other branch (`feature/…`, Dependabot, the release-please version PR), so they trigger no build and no migration.

## Versioning

[SemVer](https://semver.org) versions derived from commit messages ([Conventional Commits](https://www.conventionalcommits.org)), checked by `.githooks/commit-msg` (enabled by `pnpm install`):

| Commit | Effect on the version |
| --- | --- |
| `fix: …`, `perf: …` | patch: 1.0.0 → 1.0.1 |
| `feat: …` | minor: 1.0.0 → 1.1.0 |
| `feat!: …` or `BREAKING CHANGE:` in the body | major: 1.0.0 → 2.0.0 |
| `chore`, `refactor`, `docs`, `test`, `ci`… | none, left out of the CHANGELOG |

Same flow as patateprod-front and patateprod-back:

1. Push to `staging` as usual. release-please ([`.github/workflows/release.yml`](.github/workflows/release.yml)) keeps a "chore(staging): version X.Y.Z" PR open against `staging`: `package.json` version and `CHANGELOG.md`.
2. To release, merge that PR into `staging`: the `vX.Y.Z` tag and the GitHub Release are created.
3. Merge `staging` → `main`: Vercel deploys once, with the right version number.

Merge `staging` → `main` right after the version PR: a commit pushed in between would go to production under that number without appearing in its CHANGELOG. First version: 1.0.0 (`initial-version` in `release-please-config.json`); `package.json` stays at `0.0.0` until then.

## Deployment

Designed for [Vercel](https://vercel.com) with a [Neon](https://neon.tech) database (or any managed Postgres):

1. Create the Vercel project and connect the repo
2. Set `DATABASE_URL`, `PAYLOAD_SECRET` and `NEXT_PUBLIC_SITE_URL`
3. Connect a Vercel Blob store (adds `BLOB_READ_WRITE_TOKEN` automatically)

Migrations run automatically during each deploy (`pnpm run ci`). Never point `pnpm dev` at the production database — dev push mode would bypass the migration history.
